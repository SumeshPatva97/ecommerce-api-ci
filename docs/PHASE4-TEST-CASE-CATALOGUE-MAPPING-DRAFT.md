## 3. Method and limitations

1. **Static review only.** Test files were listed with `find`/Glob and searched with `grep`/Grep for `describe`/`it`/`it.each` names and key assertions. Selected test bodies were read to confirm what is asserted. No test, build, OpenAPI check, Prisma, database or network command was run. Whether the cited tests pass now is **not** checked here.
2. **Mocked environment.** Integration tests use Supertest against the app built with a mocked Prisma client (`tests/helpers/mockDb.ts`, `tests/helpers/container.ts`) and fake providers. "COVERED (mocked)" never means MySQL, real-provider, real-concurrency or production behaviour is proven.
3. **Concurrency rows (type C: TC-004, 030, 041, 045, 048, 051).** Mocked tests can at most simulate races (mocked P2002 unique violations, compare-and-set losses, mocked locked rows, sequential replay). Real-DB proof needs Batch 12. All type-C rows are therefore no better than PARTIALLY COVERED.
4. **Conservative grading.** A row is COVERED only when the named behaviour, including stated boundaries, is visibly asserted. An endpoint existing, or a guard being declared, was not counted as coverage. Where only part of a compound title is asserted, the row is PARTIALLY COVERED and the gap is noted.
5. **Search limits.** About 1,180 test cases were found across ~115 test files. Mapping used targeted keyword searches per row. A relevant test with an unexpected name could have been missed, so a few PARTIALLY COVERED grades could be higher after a manual check. No P1 row was found to be NOT COVERED.
6. **Out-of-scope rows.** FE/E2E (TC-053, 067, 068) and STAGING/PERF (TC-069) are not assessed. For MIXED rows only the API half is graded.
7. **No status implication.** This draft does not change or imply any project, batch or gate (G4) status. It needs independent verification before anyone uses it as evidence.
