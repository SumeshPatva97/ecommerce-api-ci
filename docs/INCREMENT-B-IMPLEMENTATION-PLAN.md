## 3. Migration strategy (proposed)

### 3.1 Tooling and compatibility

- **Prisma Migrate** workflow per P3-16: migrations as reviewable SQL files under `ecommerce-api/prisma/migrations/`.
- **Prisma 7.10.1 specifics:** datasource URL comes from `prisma.config.ts` (not `schema.prisma`); migration paths also come from `prisma.config.ts`. All migration commands run from `ecommerce-api/`.
- **MySQL 8.4 compatibility:** MySQL 8.4 enforces CHECK constraints (8.0.16+), supports generated (STORED) columns, functional/composite indexes, `utf8mb4_0900_ai_ci` default collation. Prisma maps enums to native MySQL `ENUM` column types, `Char(36)` → `CHAR(36)`, `Decimal` → `DECIMAL`, `DateTime(3)` → `DATETIME(3)` — all within supported MySQL 8 DDL.
- **Baseline strategy:** because `ecommerce_dev` is empty, Increment B is a **single initial migration** establishing the full baseline (67 tables, 50 enum-typed columns, all Prisma-expressible keys/indexes/FKs) **plus an appended SQL-only section** (§4). No expand/contract phases are needed for the baseline; expand-and-contract applies only to later post-baseline changes.

### 3.2 Folder structure and naming (proposed)

```text
ecommerce-api/prisma/migrations/
  2026MMDDHHMMSS_baseline/        # Prisma default naming: timestamp + slug
    migration.sql                 # Prisma-generated DDL + appended SQL-only section
  migration_lock.toml             # created by Prisma on first migrate (provider = "mysql")
```

- Folder slug `baseline` (or `init`) for the first migration; subsequent migrations use descriptive slugs, one concern per migration, each linked to a report/changelog entry (P3-16 §7).
- SQL-only DDL inside `migration.sql` is grouped under clearly labeled comment sections and uses explicit constraint names (`ck_*`, `uq_*`) for traceability.

### 3.3 Generation and deployment process — two candidate options (OQ-B2 — **DECIDED 2026-11-17: Option B approved**)

**Option A — `prisma migrate dev` (Prisma-native, requires a shadow database)**

1. `prisma migrate dev --name baseline` diffs the schema against a shadow database and writes `migration.sql`.
2. Requires the migration user to have DDL rights on a **shadow database** (Prisma creates/resets it; `ecommerce_dev_shadow`), which the app runtime user never touches.
3. Later `migrate dev` runs will also detect **drift** from the SQL-only objects (see risk R-4) and may propose destructive SQL — must be handled with `--create-only` + manual edits.

**Option B — offline generation + `migrate deploy` (recommended, least privilege)**

1. Generate the baseline DDL **offline, with no database access**:
   `npx prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script`
2. Create the migration folder manually; write `migration.sql` = generated DDL **+ reviewed SQL-only section (§4)**.
3. Apply with `npx prisma migrate deploy` — this executes the folder's migrations in order and records them in `_prisma_migrations`. `migrate deploy` does **not** need a shadow database and does **not** diff/detect drift (so it never auto-proposes destructive SQL).
4. All later schema changes follow the same pattern (diff → review → append SQL-only DDL → `migrate deploy`), keeping the "reviewable migration" guarantee of P3-16 without shadow-database privileges.

Option B is recommended because it (a) avoids granting CREATE DATABASE / shadow-DB rights, (b) forces explicit human review of the full SQL, and (c) avoids Prisma drift auto-fixes touching SQL-only objects. **Decision (user acceptance 2026-11-17): Option B is approved as the migration workflow; `prisma migrate dev` is not used as the production workflow and no shadow database is required.** Option A is retained above only as reviewed-and-rejected context for traceability.

### 3.4 Safe ordering within the baseline

Prisma's generated DDL already orders tables/dependencies correctly for a from-empty diff. The appended SQL-only section is deliberately sequenced **after** all table creation:

1. Supporting unique keys that are already in the Prisma schema (`uq_product_variants_id_product`, `uq_attribute_values_attr_id`) — created by Prisma DDL; no action.
2. Generated STORED columns (§4.1).
3. Conditional/composite unique indexes on generated columns (§4.2).
4. CHECK constraints (§4.3).
5. Composite foreign key `product_images(variant_id, product_id)` → `product_variants(id, product_id)` (§4.4).
6. FULLTEXT/ngram search indexes (§4.5 — **excluded from the baseline per OQ-B6 decision, 2026-11-17**; revisit only in a later approved B1–B9 decision).

No backfill steps are needed (empty database). If data ever existed, P3-16's backfill-before-contract rules would apply.

### 3.5 Rollback and recovery

- **Preferred: forward-fix** (P3-16 §6). A failed/incorrect baseline migration is corrected by a new reviewed migration or (before any data exists) by re-approving and re-running the corrected baseline against the still-empty database — never by dropping live data.
- If a migration fails mid-way (MySQL DDL implicitly commits per statement), the database may be left partially migrated. Recovery: stop, record the failing statement, restore from the pre-migration backup (§8), fix the SQL, re-apply. `migrate deploy` stops at the first failing statement and marks the migration failed in `_prisma_migrations`.
- Point-in-time recovery relies on the backup strategy (P3-18); for local dev a pre-migration `mysqldump` checkpoint is the practical equivalent (§8).
