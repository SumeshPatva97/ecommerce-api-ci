## 2. Detailed notes on the highest-priority risks

### R-4 — Drift between Prisma schema and SQL-only database objects (process risk)

After the baseline introduces SQL-only objects (generated columns G1–G10, conditional unique indexes U1–U12, CHECKs C1–C12, composite FK F1), those objects exist **only in migration SQL, not in `schema.prisma`**. Any future `prisma migrate dev` will diff the database against the schema, see "unexpected" columns/indexes, and may propose SQL that **drops the SQL-only objects**. This is inherent to the approved architecture (Prisma schema cannot represent these items; Phase 3 docs require them as SQL).

**Controls:** adopt the `migrate deploy`-centric workflow (OQ-B2 Option B) for all future schema changes; if `migrate dev` is used, only with `--create-only` plus manual review to exclude SQL-only objects; record this rule in the project development guidelines and each increment report. This risk is permanent for the project lifetime, not just Increment B.

### R-1 — Transactionality of DDL

MySQL performs an implicit commit before/after many DDL statements, so a baseline migration is **not atomic**. A failure at statement N leaves statements 1…N-1 applied. `migrate deploy` then marks the migration failed, leaving `_prisma_migrations` inconsistent with actual schema state. **Controls:** the database is empty and single-purpose; recovery is restore-from-backup (G2) and re-apply of the corrected migration; for an empty dev database this is a clean, low-drama path. Post-apply verification (plan §9) confirms final state regardless.

### R-6 — Prisma 7.10.1 / MySQL 8.4 specifics

- Prisma maps enums to MySQL `ENUM` column types and requires exact adapter/CLI version pinning (7.10.1 everywhere) — already pinned.
- Default table charset/collation derives from the database (verified `utf8mb4` / `utf8mb4_0900_ai_ci` target for `ecommerce_dev`); verification includes a per-table charset/collation spot check.
- Increment A proved the runtime adapter path (mariadb adapter, `caching_sha2_password` with loopback public-key retrieval). Database-writing migration commands do **not** use `DATABASE_URL`: they load `prisma.migration.config.ts` with `MIGRATION_DATABASE_URL`/`MIGRATION_EXPECTED_DATABASE` (fail-closed guard); the CLI uses its own MySQL connectivity (Rust engine). The scratch-DB dry run verifies this path end-to-end before the real apply.

### R-15 / R-3 — Privilege hygiene

The migration user normally holds rights on `ecommerce_dev.*` only (the approved Option B workflow uses **no** shadow database; the only extra schema is the user-pre-created `ecommerce_migrate_test` for the G7 dry run). That dev-scoped grant confers **no** privileges on the scratch database. For G7 the user applies a **temporary, scratch-scoped** grant on `ecommerce_migrate_test.*` (never `*.*`), verifies it with `SHOW GRANTS`, and revokes it once G7 evidence is accepted; G8 uses the `ecommerce_dev.*` grant and requires the `.env.migration` target switch (G3 doc §4.8). The migration user is never used by the application. Runtime user `ecommerce_app@localhost` remains SELECT/INSERT/UPDATE/DELETE only, per the explicit Increment A/instruction constraints. Any privilege verification is performed by the user locally (`SHOW GRANTS`); the agent reports only non-sensitive confirmations.
