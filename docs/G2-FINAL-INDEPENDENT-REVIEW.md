## 3. Offline dry-run results (fake client, no MySQL)

| Scenario                                | Outcome                                                                       |
| --------------------------------------- | ----------------------------------------------------------------------------- |
| Happy path (`cmd /c` restore)           | All 11 blocks OK; 12 evidence files; scratch dropped; source tables unchanged |
| Happy path (`--execute=source` restore) | Same                                                                          |
| Scratch DB already exists               | STOP at pre-check; existing schema untouched; all later blocks refused        |
| Restore modifies the source             | STOP at source check; drop refused (scratch kept for investigation)           |
| Restore exits non-zero                  | STOP; drop refused                                                            |

Test-harness substitutions (only these): client paths → shims, backup folder → scratchpad, and the
"backup folder must be outside the user profile" guard bypassed because the scratchpad is under the
profile. The `.cmd` shim truncates multi-line `-e` arguments (a shim limitation); a real `mysql.exe`
receives them intact, which was verified separately with a real executable.

## 4. Residual limitations (cannot be closed offline)

- Real `mysql`/`mysqldump` behaviour (exit codes on SQL errors inside `source`, prompt handling inside
  `cmd /c`, the exact `-- Dump completed` line) is documented MySQL behaviour but **not live-tested**.
- The drill prompts for the admin password once per command (~14 prompts); a login path
  (`mysql_config_editor`) would reduce this but stores an obfuscated credential on disk — not adopted.
- `ecommerce_dev` is expected to be empty (baseline not applied), so G2 proves the mechanism; data
  fidelity is proven again by the mandatory fresh backup before G8.
